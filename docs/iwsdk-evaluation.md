# IWSDK evaluation for MMAXR

**Evaluation date:** 2026-10-17

**Scope:** read-only comparison of the current upstream IWSDK repository with the requirements in [`skills/mmaxr-skill.md`](../skills/mmaxr-skill.md). No code, dependencies, or prototypes were changed.

**Upstream snapshot:** [`facebook/immersive-web-sdk` at `0778f518`](https://github.com/facebook/immersive-web-sdk/tree/0778f518db51e9d1836977f3b6fed9b53f3f0c6f).

**Verdicts:** “covered out of the box”, “partial”, “not covered”, and “unknown” describe evidence in the cited sources, not a claim that an app could never implement the behavior.

## B) Adoption options

1. **Stay on the existing raw Three.js + WebXR stack.**
   - **Pros:** preserves the current `0.186.1` runtime, renderer/session boundary, liquid-glass UI, phone-first behavior, and existing MMAXR controls. [MMAXR package](../packages/engine-render/package.json) · [MMAXR UI skill](../skills/mmaxr-skill.md)
   - **Cons:** MMAXR continues owning its XR systems, emulation workflow, and bespoke UI/input maintenance. [MMAXR XR runtime](../packages/engine-xr/src/session-runtime.ts) · [MMAXR spatial panel host](../packages/engine-render/src/visuals/spatial-panel-host.ts)

2. **Use IWSDK only for new modules (for example, a light lab or optics kit).**
   - **Pros:** bounds the experiment and can evaluate IWSDK's ECS, spatial UI, IWER, and agent tooling against new content. [IWSDK spatial UI](https://github.com/facebook/immersive-web-sdk/blob/0778f518db51e9d1836977f3b6fed9b53f3f0c6f/docs/concepts/spatial-ui/index.md) · [dev plugin](https://github.com/facebook/immersive-web-sdk/blob/0778f518db51e9d1836977f3b6fed9b53f3f0c6f/packages/vite-plugin-dev/README.md)
   - **Cons:** unless IWSDK can share MMAXR's renderer, scene, and action/store contracts, “module only” may mean a separate runtime/route rather than a drop-in kit; it also introduces the Three.js alias/version conflict and a second way to build modules. The shared-renderer path is not confirmed by the cited docs. [IWSDK minimal scene](https://github.com/facebook/immersive-web-sdk/blob/0778f518db51e9d1836977f3b6fed9b53f3f0c6f/docs/guides/01b-minimal-scene.md) · [MMAXR stack boundary](../skills/mmaxr-skill.md)

3. **Full migration to IWSDK.**
   - **Pros:** one SDK path for its ECS, XR input, UIKit, IWER/DevUI, and MCP/Playwright tools. [IWSDK core](https://github.com/facebook/immersive-web-sdk/blob/0778f518db51e9d1836977f3b6fed9b53f3f0c6f/packages/core/README.md) · [dev plugin](https://github.com/facebook/immersive-web-sdk/blob/0778f518db51e9d1836977f3b6fed9b53f3f0c6f/packages/vite-plugin-dev/README.md)
   - **Cons:** highest rewrite cost; unresolved exact-version and single-runtime question; MMAXR's custom glass/control/layout and precise handheld AR requirements are not supplied as matching built-ins. [IWSDK core README](https://github.com/facebook/immersive-web-sdk/blob/0778f518db51e9d1836977f3b6fed9b53f3f0c6f/packages/core/README.md) · [MMAXR UI contract](../skills/mmaxr-skill.md)

**Recommendation (five lines):**

1. **Choose option 1 now:** keep raw Three.js + WebXR for production MMAXR modules.
2. IWSDK's IWER, DevUI, MCP, managed-browser, and UIKit features are real wins, but they do not directly satisfy MMAXR's custom panel/control contract. [Vite plugin](https://github.com/facebook/immersive-web-sdk/blob/0778f518db51e9d1836977f3b6fed9b53f3f0c6f/packages/vite-plugin-dev/README.md) · [MMAXR skill](../skills/mmaxr-skill.md)
3. Its documented `super-three@0.181.0` dependency conflicts with MMAXR's current `three@0.186.1` until the single-instance strategy is resolved. [IWSDK package](https://github.com/facebook/immersive-web-sdk/blob/0778f518db51e9d1836977f3b6fed9b53f3f0c6f/packages/core/package.json) · [MMAXR package](../packages/engine-render/package.json)
4. Android handheld AR, first-frame/optional-feature ordering, and coexistence with Immersive Web Emulator 2.0 remain unverified; these are core acceptance requirements, not optional polish. [Meta test guide](https://developers.meta.com/vr/documentation/iwsdk/guides/02-testing-experience/) · [MMAXR skill](../skills/mmaxr-skill.md)
5. Reconsider option 2 only after a bounded hands-on spike answers the questions below; do not start a production migration from documentation alone.

## C) Questions for a hands-on spike

1. **Can IWSDK run inside MMAXR's existing single Three.js runtime and renderer loop?** Specifically, can `@iwsdk/core` support MMAXR's `three@0.186.1` setup, or does adoption require migrating every workspace package to `super-three@0.181.0`? 2. **Can one representative MMAXR panel group be reproduced in UIKit without compromise?** Include GlassMaterial/SDF surfaces, transparent token-driven button/slider/toggle/stepper/progress components, fixed sizing, one scale/distance pair, and no tilt/clipping. [UIKitML custom components](https://github.com/facebook/immersive-web-sdk/blob/0778f518db51e9d1836977f3b6fed9b53f3f0c6f/docs/concepts/spatial-ui/uikitml.md) · [MMAXR panel contract](../skills/mmaxr-skill.md)
3. **Does the whole device/testing path work on our target phones and current tooling?** Prove Android Chrome immersive-AR with touch, first-valid-pose/yaw-only placement, screen fallback, and no conflict between the IWSDK IWER plugin and Immersive Web Emulator 2.0. [IWSDK emulator devices](https://github.com/facebook/immersive-web-sdk/blob/0778f518db51e9d1836977f3b6fed9b53f3f0c6f/packages/vite-plugin-dev/README.md) · [Meta's documented test targets](https://developers.meta.com/vr/documentation/iwsdk/guides/02-testing-experience/) · [MMAXR device workflow](../docs/xr-device-testing.md)
